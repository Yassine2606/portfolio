## Context

Engineering teams keep their knowledge in PDF reports, Word documents, Markdown specs, and scanned paper. Finding an answer means opening files one by one, and finding a paragraph does not prove it is current, complete, or allowed to be seen. The brief was narrower than "search": a user uploads their own documents, asks a question in plain language, and gets an answer with the supporting passages attached.

I built it as my final-year project (PFE) at Capgemini Engineering, under the CRISP-DM methodology. The setting added the constraints a demo usually skips: documents are private to each user, formats are messy, LLM providers rate-limit, ingestion is slow, and a hallucinated answer in front of a client is worse than no answer.

## Problem

Four constraints shaped every decision.

- **Isolation.** Every retrieval query is scoped by user ID. A user cannot retrieve another user's chunks even if the query would match them.
- **Messy input.** PDF, DOCX, Markdown, text, and scanned images all enter the same pipeline; OCR and table-structure inference run before chunking.
- **Slow ingestion.** Parsing and embedding cannot block the chat, and a failed job must be retryable.
- **Unsupported answers.** The product cannot ship fluent guesses. When the evidence is insufficient, the assistant must ask a clarifying question instead.

## Decisions

### Hand-written retrieval instead of a framework

No LangChain, no vector-store SDK, no orchestration runtime. Parsing, chunking, embedding, RRF fusion, and the tool loop are explicit code. The cost is more surface area to maintain. The benefit is that every retrieval decision is inspectable and every failure has a location — which matters when the product claim is "the answer is grounded."

### Verification as a second model call

A single generation call is cheaper and faster. It also cannot tell you whether it followed the evidence. The separate verifier adds latency and cost per answer, but it converts "the model usually cites sources" into a checkable gate. On failure, the query is refined once; if it still cannot be grounded, the assistant asks a clarifying question.

### Asynchronous ingestion with a degraded mode

BullMQ and Redis make uploads non-blocking and retries explicit. The interesting decision is what happens when Redis disappears: the queue marks itself unavailable and processes inline, then reconnects. This is more code than a hard dependency, but document processing does not die because one service restarted.

### Local embeddings, with a known weakness

all-MiniLM-L6-v2 runs locally, costs nothing per query, and keeps documents off a third-party embedding API. It is also English-centric. On French and Arabic content, retrieval quality is the weak link. A multilingual model or hosted embedding service is the upgrade path; the current choice is a deliberate cost and privacy trade, not a claim of multilingual quality.

### Summary memory instead of unbounded history

Long conversations are folded into a structured summary stored on the conversation row. This loses detail. It also keeps the context window bounded and predictable, which is the difference between a demo that works for three turns and a product that works for thirty.

## Reliability

| Failure                           | What the system does                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------ |
| Provider rate limit or outage     | Tries the next provider in the chain; maps the failure to a stream error the UI can render |
| Redis unavailable                 | Degrades to inline document processing, then reconnects                                    |
| Answer cut off at the token limit | Resumes from the detected overlap instead of restarting                                    |
| Stale chunks after re-upload      | Deletes the document's previous chunks before inserting new ones                           |
| Unsupported answer                | Fails verification, retries once with a refined query, then asks a clarifying question     |
| User cancels a stream             | Abort controller stops the request; the optimistic message is reconciled                   |

The honest limits: there are no automated tests around the retrieval or agent loops, and the multilingual embedding weakness is real. Those are the first two items in the next section.

## Outcome

A working end-to-end system, not a measured product. The pipeline has nine stages across eight services; ingestion is asynchronous; retrieval is hybrid; every answer passes a verification gate before it reaches the user. The private repository contains the implementation.

That distinction is the point of the evidence margin. The system is real; the proof is partial; the page says which is which.
