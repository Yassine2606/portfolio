## Context

Databases degrade without announcing it. Nulls accumulate, keys duplicate, schemas drift, queries slow down, endpoints start returning 500s. General observability tools raise an alert, but "table scans increased" still leaves a developer to work out what changed and what to do.

The brief was an agent that reads databases and endpoints with read-only access, detects data-quality, performance, and availability anomalies, and hands each finding to an LLM that writes a plain-language explanation, a severity, and a fix with an impact and effort estimate. Two constraints shaped it: the monitor must never write to a production database, and the whole system must run as a demonstrable product without live infrastructure.

## Problem

The project had to solve four things at once:

- **Three dialects.** PostgreSQL, MySQL, and MongoDB expose schemas and samples differently. Detectors should not care which database produced a signal.
- **Rules before prose.** An LLM cannot reliably find a missing index. Detection stays deterministic; the model explains findings rather than inventing them.
- **A demo with no infrastructure.** The system ships with fixtures for all three databases and an in-memory report store, so a full scan runs anywhere.
- **A protocol surface.** The MCP server had to expose scans and reports as tools, not just exist as a library.

## Decisions

### Read-only in the scan path

The connectors expose read methods for schema metadata, counts, samples, and query statistics. No scan step issues a write, and the constraint is visible in the code rather than in a README promise.

<Claim

  n="1"
  source="src/monitors/database.py + src/api/main.py"
  kind="repo"
  href="https://github.com/Yassine2606/anomaly-detection-agent"
  note="Public repository. The read-only rule covers the monitor methods; it is a code-level constraint, not a database grant."
>
  The PostgreSQL, MySQL, and MongoDB monitors only read schema metadata, row counts, null counts,
  and duplicate keys. The scan flow contains no INSERT, UPDATE, DELETE, or write aggregation.
</Claim>

### Detection is deterministic; the model explains

Gemini is not asked "find anomalies." Detectors classify signals with explicit rules — null ratios, duplicate keys, schema consistency, foreign-key violations, slow-query flags, missing-index heuristics, status-code and latency regressions. Only flagged findings reach the model, which returns severity, explanation, and a recommendation. This keeps the expensive, non-deterministic step away from the detection boundary.

### A seeded store instead of a live dependency

The demo strategy is an in-memory store seeded from fixtures for all three databases. It makes a full scan reproducible on any machine. It also hides persistence, scale, and recovery questions — which is why the case study labels it a demo strategy, not an architecture.

### MCP as a real surface, with an honest boundary

The FastMCP server exposes four tools over stdio: scan anomalies, get anomalies, get statistics, and clear anomalies. It is a working protocol surface. It is not yet the real system.

## Reliability

The reliability story is mostly about refusing to overstate what exists.

  stated here and in the repository's own lessons rather than papered over with a badge.

| Risk                      | Current behaviour             | What is missing                                  |
| ------------------------- | ----------------------------- | ------------------------------------------------ |
| Real database through MCP | Mock scan only                | Connector wiring into the MCP tools              |
| Restart or scale          | In-memory store loses reports | Durable report storage                           |
| Test coverage             | No committed tests            | Unit tests for detectors, API, and agent parsing |
| Recommendation quality    | Model output is advisory      | A labeled benchmark of findings and fixes        |
| Credential scope          | Read-only connectors          | A documented least-privilege role per database   |

## Outcome

The system works end to end on seeded data: three read-only connectors, three anomaly classes, a Gemini explanation layer, nine HTTP routes, a React dashboard, and an MCP server with four tools. The public repository lets someone verify each of those claims.

It is not a production monitoring product. The MCP integration is partial, persistence is in-memory, and the recommendation layer is unevaluated. Those are the next three pieces of work, in that order.

## Next

- Wire the real connectors into the MCP server and remove the mock-only limitation.
- Add durable report storage and a scheduled scan runner.
- Write the missing tests, starting with detector rules and API contracts.
- Build a labeled set of anomalies and measure explanation precision before calling the recommendations reliable.
